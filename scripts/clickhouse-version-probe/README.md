# ClickHouse version compatibility probe

Verifies that the SQL generated by the AgentObs query providers passes `EXPLAIN SYNTAX` and
actually runs on a given ClickHouse
version. Written for the 21.8.14.5 deployment target, which is nine major-ish versions behind
the 25.12 development instance and is missing at least one function the provider used to call.

## Why this exists

A provider unit test can only assert on SQL *text*. It cannot tell you whether the server
accepts that text. The 21.8 check found a real defect that every unit test had passed:
`length(JSONExtractKeys(...))` does not exist on 21.8 and raised
`Received exception from server`. The provider now uses `JSONLength`, which exists on both.

Run this whenever the target server version changes, or after editing the provider.

## Prerequisites

- A running ClickHouse at the version under test.
- The backend compiled (`mvn -o compile` in `backend/`).
- A local JDK 8.

## Run

```bash
# start the version under test (example: the 21.8 target)
docker run -d --name ch218-verify --memory=1500m -p 8124:8123 \
  clickhouse/clickhouse-server:21.8

# create the schema on it
docker exec -i ch218-verify clickhouse-client --multiquery \
  < backend/sql/clickhouse/agentobs-clickhouse-schema-local.sql

# render every provider statement and execute it against that server
cd backend && mvn -o -q dependency:build-classpath -Dmdep.outputFile=/tmp/cp.txt
CP="target/classes:$(cat /tmp/cp.txt)"
javac -encoding UTF-8 -cp "$CP" -d /tmp/probe scripts/clickhouse-version-probe/SqlCompat.java
java -cp "$CP:/tmp/probe" -Dch.url=http://127.0.0.1:8124/ SqlCompat
```

The expected count is printed by the probe. A failure prints the offending SQL and the server error.

## DriverProbe

Checks that the pinned `clickhouse-jdbc` 0.4.6 can connect to the target and bind parameters
against the new schema, which the SQL-only probe does not cover.

```bash
javac -cp "$CP" -d /tmp/probe scripts/clickhouse-version-probe/DriverProbe.java
java -cp "$CP:/tmp/probe" DriverProbe   # edit the URL inside for a different port
```

| ClickHouse 25.12.11 | 48/48 | n/a | the development instance, `_all` as a View |
| ClickHouse 25.12.11, `_all` as Distributed | 26/26 | n/a | the cluster shape - see below |

After the trace-detail locator-bound change on 2026-09-15, the current local ClickHouse

execution). The added check covers the shared, explicitly typed UTC locator bounds in
`traceMetrics`. The 21.8 and Distributed results above are historical runs of the earlier
probe set; the new 49-check set has not been rerun on those targets.

## Verifying the cluster shape

`_all` is a View on a single node but a **Distributed** table in the cluster, and the two do not
behave the same for `FINAL`. Reproduce the cluster shape locally by giving the server a
one-shard cluster and building `_all` as Distributed:

```bash
cat > /tmp/chcluster/cluster.xml <<'XML'
<clickhouse>
  <remote_servers>
    <verify_cluster>
      <shard><replica>
        <host>127.0.0.1</host><port>9000</port>
        <user>verify</user><password>verify</password>
      </replica></shard>
    </verify_cluster>
  </remote_servers>
</clickhouse>
XML

# 25.12 images require credentials
docker run -d --name chcluster-verify --memory=1500m -p 8125:8123 \
  -e CLICKHOUSE_USER=verify -e CLICKHOUSE_PASSWORD=verify \
  -v /tmp/chcluster/cluster.xml:/etc/clickhouse-server/config.d/cluster.xml:ro \
  clickhouse/clickhouse-server:25.12

docker exec -i chcluster-verify clickhouse-client -u verify --password verify --multiquery \
  < backend/sql/clickhouse/agentobs-clickhouse-schema-local.sql

# replace the _all Views with the Distributed tables the cluster actually has
for t in traces observations scores span_events span_links logs metric_points; do
  docker exec chcluster-verify clickhouse-client -u verify --password verify --query "
    DROP VIEW IF EXISTS default.hmp_agentobs_${t}_all;
    CREATE TABLE default.hmp_agentobs_${t}_all AS default.hmp_agentobs_${t}
    ENGINE = Distributed(verify_cluster, default, hmp_agentobs_${t}, xxHash32(trace_id));"
done

java -cp "$CP:/tmp/probe" -Dch.url=http://127.0.0.1:8125/ -Dch.user=verify -Dch.password=verify SqlCompat
```

### Result: FINAL differs by shape, and both are correct

Insert one row and a replay of the same `(trace_id, span_id)` with a higher `ingestion_version`:

| | Physical | `_all` without FINAL | `_all FINAL` |
|---|---:|---:|---:|
| Local, `_all` = View | 2 | **2** | **2** (FINAL ignored) |
| Cluster, `_all` = Distributed | 2 | 2 | **1** (pushed down) |

So a plain view silently ignores `FROM view FINAL` on **both 21.8 and 25.12**, while a
Distributed table honours it. That is why the local schema defines its views with `FINAL`
inside them, and why the cluster needs no such workaround. The provider emits the same
`_all FINAL` in both cases and is correct in both - but only because of that view definition.

The AggregatingMergeTree locator also behaves correctly through Distributed: the MV backfills
on insert, `minMerge`/`maxMerge` collapse states across the shard boundary, and the provider's
`traceLocator` query returns the right service and time range.

## Also worth checking on a new target

These are not covered by the probe but matter for the same migration:

1. `CREATE VIEW … AS SELECT … FINAL` and whether `FROM view FINAL` is honoured through it.
   On both 21.8 and 25.12 a *plain* view silently ignores `FINAL` - see
   `upgrade-views-add-final.sql`. Confirm the version under test behaves the same, because
   the whole deduplication fix depends on it.
2. `CREATE OR REPLACE VIEW` availability, which the upgrade script needs (present on 21.8).
3. `ttl_only_drop_parts` and `index_granularity` table settings.
4. `system.query_log` column names, if any tooling reads them (21.8 differs from 25.12).
